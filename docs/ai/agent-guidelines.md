# Choosing components and composing application features

1. Start with the user action. A tab changes the visible panel, a route changes the page, and a dialog temporarily interrupts either. Look up the component by purpose in the [inventory](README.md) and follow its source link.
2. Check namespace, generic arguments, EditorRequired properties, and fragment names before writing markup. For two-way binding find both the value and matching callback. Checkbox and switch bind Checked, select binds Value, and dialog binds Visible. A captured unmatched attribute can compile as HTML even when a misspelled parameter has no effect.
3. Use a small application component when several screens share domain markup, such as an OrderStatusBadge or an AppointmentSummary. Give it an application namespace. The release has no public advanced scheduler, calendar booking engine, point-of-sale terminal or payment workflow. Compose a list with UiDataGrid and UiDatePicker for day selection, and design booking or settlement rules in a separate service.
4. Accept only permitted sort and filter fields in server providers. Enforce tenant boundaries, permissions, write validation and concurrency checks on the server, including on export. Pass cancellation tokens into I/O. Keep domain models, persistence and remote credentials out of presentation components.
5. Give fields visible labels and icon buttons action names. Test opening a dialog, Tab and Shift+Tab, Escape, and return to its launcher. Test a narrow viewport, long names, both themes and RTL. Keep critical data available when hiding a column on mobile. For charts supply a textual summary or table.
6. Compile examples against the pinned public packages with the [documentation gate](audit.md). Use browser and assistive-technology checks for interaction and announcements that compilation cannot establish.
